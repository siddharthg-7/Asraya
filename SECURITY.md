# Pramāṇa Security Policy & Security-First Architecture

## 1. Security Philosophy

Pramāṇa is designed from first principles around **Data Minimization**, **Zero-Knowledge**, and **Unlinkable Proofs**. Its fundamental paradigm is **"Move the Question, Not the Data."**

Security is not an afterthought or an add-on library; it is enforced through the four-tier architectural model, cryptographic proof systems, and strict anti-hallucination development rules.

---

## 2. Core Protected Assets

The system is architected to protect the following critical assets:

1. **Citizen Credentials**: Signed attribute sets issued to citizens containing sensitive personal, identity, financial, or academic data.
2. **Citizen Wallet Private Keys**: Holder-binding private keys used to derive blinding factors, proof signatures, and non-custodial authorization.
3. **Issuer Private Signing Keys**: Root authority keys used to sign BBS and credential structures.
4. **Verifier Private Decryption/Signing Keys**: Keys used to decrypt end-to-end encapsulated payloads (HPKE) and sign Verifier Request Contracts.
5. **Consent Signatures & Receipts**: Verifiable cryptographic evidence that a citizen authorized a specific bounded question for a designated purpose.
6. **Proof Data Envelopes**: Transient zero-knowledge proofs and selective-disclosure representations generated by the wallet.
7. **Registry Trust Checkpoints**: Authenticated Merkle roots and public key digests distributed to allow offline verification.
8. **Audit Receipts**: Immutable logs of verification outcomes containing no raw citizen data.
9. **Context-Scoped Nullifiers / Pseudonyms**: Ephemeral, unlinkable identifiers that prevent double-spend or duplicate claims within a single verification context while preventing cross-context tracking.

## 3. Cryptographic Governance & Standards

### Tier A: BBS Signatures (Default Proof Tier)

- **Standard**: IETF CFRG BBS Signature Suite over BLS12-381.
- **Properties**:
  - Multi-message selective disclosure without revealing undisclosed messages.
  - Native proof of possession and holder blinding.
  - Predicate evaluation via bit-decomposition commitments.
  - Unlinkable randomized zero-knowledge presentations.

### Tier B: Groth16 zk-SNARKs (Fallback Proof Tier)

- **Standard**: Circom constraint systems verified with Groth16 over BN254 / BLS12-381.
- **Constraints**:
  - Used ONLY for complex multi-attribute non-linear predicates that cannot be efficiently evaluated via BBS bit-decomposition.
  - Proving keys and verification keys must be cryptographically tied to trusted registry checkpoints.

---

## 4. Key Security Invariants

1. **No Raw Attribute Storage**: Verifier databases must NEVER persist raw citizen attributes. Only minimal verification state (session ID, timestamp, verdict, receipt hash) may be retained.
2. **No Raw Attribute Logging**: Log redaction middleware strictly prevents printing decrypted claims, citizen names, national IDs, or financial values to console or persistent log stores.
3. **Strict Replay & Temporal Bounds**: All verifier requests contain a cryptographically random nonce and a short-lived expiration timestamp (default: 60–120s). Nonces are checked for freshness and burned upon presentation.
4. **Non-Custodial Key Ownership**: Wallet private keys never leave the client device or secure enclave. No server or custodian possesses citizen signing keys.
5. **Template-Bound Consent**: Consent prompts rendered to citizens are constructed exclusively from verified registry templates to prevent spoofed or misleading verifier text.

---

## 5. Vulnerability Disclosure & Escalation

If you identify a security vulnerability within Pramāṇa:

- Do NOT open a public GitHub issue.
- Document the issue with reproducible proof-of-concept steps.
- Escalate immediately according to project security protocols.
